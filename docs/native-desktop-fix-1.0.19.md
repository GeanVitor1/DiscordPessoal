# Native input and assistance view correction

The 1.0.18 helper performed desktop binding on its protocol/STA thread, accepted only a desktop literally named Default, and classified open/query/bind/cursor failures as DESKTOP_UNAVAILABLE. The UI unconditionally translated that into a protected/locked-screen warning. Therefore the displayed warning did not establish that the screen was locked.

An isolated regression fixture put the old protocol thread on a private inactive desktop with an owned hook. The visible Windows input desktop stayed unchanged. STATUS reproduced `DESKTOP_UNAVAILABLE:SWITCH:170` in the 1.0.18 source. The baseline is recorded in `docs/validation/desktop-busy-baseline.json`. This reproduces a real defect with the same misleading warning; the old physical-PC logs recorded only the aggregate code, so they cannot establish the exact sub-error seen on the other PC.

The Windows API [rejects SetThreadDesktop when a thread already owns windows or hooks](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setthreaddesktop). The helper now dispatches input serially to a dedicated MTA worker, checks the actual input-desktop flag, and recreates that worker once if binding fails before injection. Input ordering, native acknowledgements and release of held keys/buttons are preserved.

[GetUserObjectInformation's UOI_IO](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getuserobjectinformationw) identifies the desktop receiving input. The code uses that flag rather than equating every non-Default name with a protected desktop. Winlogon and secure screen-saver names are still refused, as are OS access/integrity restrictions. Only read/query rights are requested to obtain the input-desktop handle. No SwitchDesktop call changes the user's visible desktop.

The helper reports access, query, binding, inactive-desktop and cursor failures separately. Both sides retain the native error detail over the assistance DataChannel; the host also records that detail in the normal application log. The unchanged server supports existing fallback acknowledgement codes but does not forward the optional detail field; full detail remains available on the host in that fallback mode.

Monitor lookup now uses a trusted, native-grant-bound IPC endpoint and screen-only enumeration without thumbnails or window icons. Every lookup validates the consenting renderer, session and monitor before and after awaiting the capturer. It cannot capture an unauthorized monitor, and assistance still owns its separate capture/connection.

The guest view is expanded by default, has full-screen and compact controls, and keeps the toolbar outside the coordinate surface. The host receives a compact status notification with no empty video panel. Resize/full-screen changes use the existing normalized monitor coordinate mapping. Control is confirmed only after a successful native acknowledgement.

Acceptance includes the busy-protocol-desktop fixture plus real SendInput into an owned Windows window from two packaged clients. It checks large/full-screen/compact clicks, buttons, drag, scroll, Unicode, shortcuts, held-input release and independent share/assistance teardown. The inspector harness disables external Google Fonts requests and uses OS font fallbacks to avoid waiting on external stylesheet loads; the distributed app's fonts are unchanged. Physical two-PC, external NAT/TURN, secure-desktop transitions and real UAC acceptance remain separate limitations.

Final validation: 19 root tests, 28 client tests, source desktop smoke, native SendInput, ACL/PID-verified local native relay, packaged UI and the complete two-client acceptance passed. The NSIS payload matches the validated application and freshly compiled helper. A separate MouseWithoutBordersHelper retained Windows foreground ownership during earlier tests; after the user exited it, large/full-screen/compact clicks and the full independence/revocation flow passed. That test interference is distinct from the reproduced 1.0.18 binding defect.
